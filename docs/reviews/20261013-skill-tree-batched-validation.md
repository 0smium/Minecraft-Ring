# 技能树、动态能力规则与单人联机验证

2026-10-13 · 需求设计与源码核对；未实现、未安装、未实机测试。项目基线 `e2188391b5ba1257a9853920244909decf3bd97f`，延续 [MC 能力与联机 review](20261013-mc-abilities-multiplayer.md)。

本次用户确定：法环升级给予技能点，在技能树升级能力，并控制 ClickGUI、TabGUI、config 的可见性及可调范围。后续按功能组开发，在一次部署中验证多个内容，不再把每个可独立推进的小项都变成下一项的前置条件。

## 1. 参考与选型

| 参考 | 借鉴或复用内容 | 对本项目的选择 |
| --- | --- | --- |
| Pufferfish's Skills | 数据驱动图谱、节点连接、解锁与点数、界面、API、自定义 reward、数据重载 | 优先作为技能树依赖，Bridge 编写自己的能力适配；保留 MC 1.21.1 |
| Skill Tree（RPG Series） | 攻守专精、改变技能用法的关键节点、洗点 | 借鉴分支与取舍；它是内容模组，依赖多个职业模组，不需为树 UI 引入整套战斗系统 |
| Passive Skill Trees | 类 PoE 的图谱、路径规划、有限点数形成不同构筑 | 借鉴图谱阅读与大节点设计；所读默认源码为 1.20.1，不作为当前 Fabric 底座依赖 |

官方发布列表有 `puffish_skills-0.19.2-1.21-fabric.jar`，标注支持 1.21.1、2026-10-08 发布、Beta；版本表将 1.21–1.21.1 Fabric 列为维护中。适配候选固定到这个版本，共载和完整依赖仍需实测，不能把元数据兼容写成运行通过。无需为技能树先升级到 26.3。

源码核对 `pufmat/skillsmod` 的 `1.21` 分支提交 `78485d944719516667e648398e6d469b059c8c32`：

- `Common/src/main/java/net/puffish/skillsmod/api/Category.java` 有按来源 `Identifier` 分组的 `setPoints`、`addPoints`、总点数/已花费/剩余点数查询，以及打开界面、洗点接口。
- `api/SkillsAPI.java` 有解锁、锁定、新点数事件和自定义 reward 注册；`api/reward/Reward.java` 有 `update` / `dispose` 生命周期。可以注册 `erbridge:capability`，在能力变化后重新计算整份规则。
- `Fabric/src/main/java/net/puffish/skillsmod/main/FabricMain.java` 接入 `END_DATA_PACK_RELOAD`；官网明确 JSON 配置支持 `/reload`。Bridge 自己的策略校验、回滚和 LB 界面刷新仍需实现。
- 普通点选沿用框架的服务端解锁校验，不拿管理员强制解锁接口代替玩家消费点数。API 示例采用 Yarn 名称，本工程使用的映射不同，适配时使用构建工具的映射结果。

这些项目的设计参考与代码复用是不同选择：Pufferfish 作为独立依赖通过公开 API 接入；它的公开源码许可证为 All Rights Reserved，不把源码或美术直接复制进本仓库。

## 2. 图谱先做少量有区别的能力

建议先画四支：迅捷、自动近战、术法、防御/工艺。首批实际开放前两支，其余不显示可购买的空功能。未学节点在技能树中显示下一步收益，操作 GUI 只暴露已授权能力；未学模块也可按预设显示灰色锁定状态。

| 能力 | 解锁 | 升级方向 | 实现限制 |
| --- | --- | --- | --- |
| Speed | 开放一种已测移动模式 | 提高地面速度预算；后续选择持续加速或短时冲刺 | 不能把 LB 所有绕过模式一起开放；跑跳、计时器、坐骑与击退另定预算 |
| Aura | 开放单目标自动近战 | 提高有效距离；再选择范围或多目标专精 | 同时约束目标、视线、攻击冷却和墙后攻击，不能只改一个 Range 滑块 |
| 术法 | 对应原生施法能力完成后开放 | 法术槽、动作组合或资源效率 | 法环现有属性收益和新增收益各结算一次 |
| 防御/工艺 | 对应装备/制作能力完成后开放 | 弹反容错、格挡代价或新配方 | 以具体执行效果为准，不解锁尚未支持的原生行为 |

Speed 的 `+10% / +20% / +35%`、Aura 的 `2.5 / 3.0 / 3.5 MC 格`可作为初始调参示意，不是已验证的平衡数值。Speed 先选一个模式标定实际位移；Aura 范围必须与服务端、代理实体和 ER 坐标换算一致。小节点增加数值，大节点改变用法，避免只有一条不断增大的滑块。

初版用稳定 ID 的连续节点表示等级，例如 `speed_1 → speed_2 → speed_3`；规则将已学节点折算成能力等级。UI 后续可合并显示为“Speed 2/3”，不先重写整套图谱。长期存档允许持续成长；UHC 使用每局独立的点数、上限和专精预设。

## 3. 法环升级发点与存档

单人/合作成长预设默认每提升一个法环角色等级获得 1 点；MC 经验仍可用于附魔等原玩法，不自动成为第二个技能点来源。先保存绑定时的角色等级作为起点；旧角色是否补发由显式的导入预设决定，避免第一次连接突然得到几百点。

记录键至少含 MC 玩家 UUID、玩法存档/对局 ID、ER 角色绑定 ID；角色绑定不能使用进程 ID 或临时指针。宿主会话 ID 只用于拒绝旧会话消息，重启不能当成新角色重新发点。

建议维护起始等级 `L0`、已确认最高等级 `Lmax`、每级点数 `p` 和一次性起始点数 `P0`。累计应得点数为 `P0 + max(0, Lmax - L0) × p`，剩余点数由图谱扣除已花费部分。

利用已核对 API，给图谱设置来源 `erbridge:er_level` 的**累计点数**，而非每次收到等级包就调用 `addPoints(1)`。这样重复包、重连及重新同步相同等级不会再次增加点数。起点、最高等级和角色绑定先持久化，再对框架点数做幂等校准；重启继续核对未完成的同步。

法环等级读取仍需增加正式桥接字段和有效状态。只接受已加载角色的稳定快照；读条中的 0、临时不可读、回滚或更换角色不能误判成升级。洗点返还已花费点数，法环属性重分配不再次发点；降低/修改等级的调试操作单独处理。管理员修改发点曲线时需要迁移规则，不能无提示地扣出负点数。

Pufferfish 保存节点和消费结果，Bridge 保存等级来源/角色绑定；不要再维护一份可独立消费的 LB 点数余额。登录、死亡重生、洗点、规则 reload 后从权威节点重建能力快照，reward 回调不能靠反复“加一次属性”积累效果。

多人公平性边界：客户端上报的原生等级并非可信的防作弊证明。熟人合作可采用上述等级绑定；竞技 UHC 的成长额度应由 MC 服务端对局记录裁决，并协调法环升级。防重复发点不等于防止修改客户端伪造等级。

## 4. 技能如何控制 GUI、配置和实际执行

MC 逻辑服务端保存技能状态并生成带修订号的能力快照；客户端薄适配读取快照。快照至少描述：模块是否可见、是否可用、允许的模式、可编辑字段、动态范围、消耗与冷却。ClickGUI、TabGUI、配置导入、命令/脚本、快捷键和模块运行使用同一份规则。

固定核对 LB `e5a0dbf5458b063d3028e69e04762b8b25b998b5`（当前 1.21.1 路线）：

| 源码入口 | 已有能力 | 需要补的部分 |
| --- | --- | --- |
| `features/module/ClientModule.kt` | `enabled` 开关、`running`、enable/disable、可选 Locked | 在启用副作用之前检查授权；撤销权限时正确 disable 并清理状态 |
| `integration/interop/protocol/rest/v1/client/ModuleFunctions.kt` | 模块枚举、切换、读取与写入设置 | 当前枚举所有模块；增加可见/锁定信息和服务端规则校验 |
| `config/ConfigSystem.kt`、`config/types/Value.kt` | 配置导入、通用 setter、`ValueChangedEvent` | 导入与脚本写值也要校验；规则变化后重新约束已保存值 |
| `config/types/Value.kt` 的 `RangedValue` | 声明时固定的 `range` | 增加有效范围，UI 不能继续展示完整上限 |
| `config/gson/serializer/ConfigurableSerializer.kt` | 文件、公共配置与 interop 序列化分开 | 各入口共享策略，不能只过滤公共配置 |
| `integration/theme/component/ComponentType.kt` | 已列出 `TAB_GUI` | 本次未核对打包主题前端；它与 ClickGUI 都需接收策略刷新 |

现有 `hidden` 变更主要通知 HUD 列表，REST 仍返回全部模块；它不是技能可见性系统。`Locked` 也是本地配置，并非服务端授权。

两个容易误做的细节：`Value.set` 的多个 onChange 监听器分别收到原始输入，后面的返回值可能覆盖前面的截断；而 `enabled` 现有 onChange 会调用 enable/disable。不能简单在末尾追加一个监听器就认为已阻止启用。策略必须位于副作用前，并在实际执行路径再次检查。撤销时也不能先设 Locked 再期待其短路分支执行清理。

保存“用户偏好值”和“当前生效值”两个概念，但只让后者参与执行。导入超限值可以明确拒绝或截断；不得覆盖服务端解锁状态。Config 页面/公共导出只暴露当前允许项；本地存储即使保留暂不可用的偏好也不能据此执行。新解锁功能默认等待玩家启用，避免升级瞬间自行攻击。服务器仍校验实际速度、距离、冷却和伤害，不能只依赖定制客户端自律。

为了统一 GUI 和配置入口，建议这一批就做固定 LB 版本的薄定制层；有必要修改 LB UI/API 时维护薄 fork。成长账本和树定义留在 Bridge/玩法组件，Meteor 以后另写同一能力协议的适配器，不同时维护两套成长规则。

## 5. 热更新边界

| 变化 | 目标行为 | 是否需要重启 |
| --- | --- | --- |
| 获得点数、点选升级、洗点 | 服务端确认，推送最新节点/能力，刷新打开的界面 | 不需要 |
| 既有能力的上限、代价、节点连接 | 校验数据，重载图谱与能力策略，重新计算在线玩家状态 | 设计为不需要；需验证框架与适配层一致更新 |
| 能力被撤销或参数降低 | 当前 tick 应用新限制；停用并清理该能力持有的计时器、旋转/按键等状态 | 不需要 |
| 新增图标或资源 | 走相应资源刷新；与服务端数据重载区别处理 | 视资源加载方式 |
| 新增 Java/Kotlin 实现、Mixin 或原生 DLL/地址适配 | 重新构建对应制品 | 通常需要 |

不把“技能状态实时同步”称为重载整个模组。已有值变化事件不保证 UI 会重拉模块清单和滑块范围，应增加带修订号的策略刷新通知。服务端在同一规则版本内裁决请求，拒绝旧版本购买/配置操作，客户端随后获取完整快照。

树配置先校验再应用；保留稳定节点 ID。删除节点、改前置或提高成本时显式迁移/退款。错误配置保留上一个有效策略是 Bridge 的待实现要求，不能假定框架所有错误情况已经自动回滚；研发时先预检配置再发 `/reload`。

## 6. 按功能组开发和验收

下一批建议交付“成长与能力组”，一次配套安装包含：

1. 法环等级有效快照、角色绑定及点数来源持久化。
2. 技能树页面、两条分支、解锁升级和洗点。
3. Speed/Aura 两个真实 LB 模块的模式/参数授权与运行约束。
4. ClickGUI/TabGUI/config 联动与数据重载。
5. 调试状态页显示角色绑定、等级、点数、策略修订和生效上限；提供可控的测试后端。
6. 独立 MC 服务端启动检查、双客户端身份隔离测试；将受击/死亡广播改为按宿主归属路由的小样，并与成长同步一起验收。

这些是同一批的实现与验证范围，不要求等一个小项彻底打磨完再开始下一个。提交仍按组件保持可定位，最后组成一套版本固定的 DLL、Bridge、LB 与依赖；“一次只加载一组配套制品”不等于“一次只能测试一个功能”。

共用一次测试流程：首次绑定 → 法环升两级 → 分别学习 Speed/Aura → 调节 GUI → 导入超限 config → 热改上限 → 洗点 → 死亡/重进 → 双客户端分别升级 → 对 A 注入受击 → A 断线重连。每一步分别记录通过、失败、未测及真实/模拟后端；目标是不重复启动一整套游戏去验证彼此可共用场景的小项。

发布时记录逐项结果，非阻塞的 UI/数值问题进入后续修整；会造成崩溃、重复发点或存档损坏的问题挡住依赖它的玩法，其余不受影响的能力继续推进。DLL 与模组的部署/验证仍在可运行游戏的环境进行，本轮没有这些结果。

下一组可同时做 MC 马、一次隐藏角色施法、背包/一件装备操作、贴怪接触与自身调试怪清理；它们共用相同的场景和状态面板。完整施法表、任意地形删除及 AI 导航重建另列，不占住成长组交付。

## 7. 一个人验证联机

一个人可以控制两个客户端；需要区分网络参与者数量和操作人数。

| 环境 | 可验证内容 | 不能据此认定的能力 |
| --- | --- | --- |
| 一个 MC 服务端 + 两个 MC 客户端 + 模拟 ER 后端 | 玩家点数/技能隔离、同步、重连、重复事件、规则 reload、结算 | Seamless 共载、原生敌人同步、真实施法 |
| 一套真实 ER/Bridge + 两个 MC 客户端 | 单宿主事件仅影响绑定玩家、另一玩家旁观、桥接消息与 UI 联动 | 第二名玩家拥有独立 ER 身体，或两侧原生敌人一致 |
| 两套真实 ER/Bridge + 同一个 MC 服务端 + Seamless | 原生玩家/敌人/攻击同步、重复伤害/奖励、断连与坐标一致 | 尚未测过的跨图、任意 Boss 和大规模联机 |

先提供双客户端启动配置：隔离游戏目录、日志、身份与端口。用合法的独立客户端身份；若采用本地开发测试身份，仅在绑定回环地址的隔离测试服使用。机器人可补重复事件和重连测试，但不能替代真实客户端的 GUI 或 ER 共载验证。

完整测试可以由一个人轮流操作两台设备上的 A/B：同一区域汇合 → 只让 A 受击 → 分别打同一只普通怪 → 确认一次死亡/奖励 → B 重连 → 检查方块/坐骑和技能状态。第二个角色可以大部分时间站着，不需要找第二个人持续配合。

只有一台电脑时，多开 ER 是额外实验，不能承诺直接可用：要解决 Steam 会话、两个游戏进程、显存和输入焦点。Seamless 官方要求 Steam 在线及游戏/模组版本一致；本轮没有核实单个 Steam 会话双开加入自己的可行性。先用一套真实 ER 加两个 MC 客户端完成预检，不为预检先购买设备。

当前项目源码还有三个明确前提：

- `ErLink.java` 是进程级单例，通过本地 `bridge.shm` 与一个宿主通信；`CombatBridge`、`LifeBridge` 在服务端直接消费这个宿主状态。远程专用服读不到各玩家电脑上的共享内存，需要客户端网关把带玩家/宿主身份的数据转发给服务端。
- `CombatBridge.onServerTick`、`LifeBridge.onServerTick` 遍历所有玩家施加同一次受击/死亡。双客户端测试会触发既有 R01/R02；应先增加绑定与定向路由，不能把当前包直接部署为多人成功方案。
- 共享内存文件名固定，但目录已有隔离入口：原生 `src/log.cpp` 读取 `ERMC_DIR`，MC `BridgePaths.java` 读取 `erbridge.dir` 或 `ERMC_DIR`。两套配对实例可分别配置目录，避免交叉读写 `bridge.shm` / `frames.shm`；这只解决 IPC 文件冲突，不证明两套 ER/Steam 能同时运行。专用服不直接抢占客户端同一个控制区。

独立服务端的启动与客户端类隔离也要先测；`fabric.mod.json` 写 `environment: *` 不构成验证。所有测试后端事件都带明确来源标记，最终报告分别写“MC 多人规则通过”“单宿主桥接通过”“双 ER 共载通过”，不合并成笼统的“已支持联机”。
