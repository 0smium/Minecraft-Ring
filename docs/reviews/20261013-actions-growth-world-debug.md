## 1. Bridge 的目标是完整角色操作

“只读背包 → 一次装备操作”是第一条可验证切片，不是组件的最终边界。目标是在 MC 界面与控制方式下使用法环角色能力，正常流程不需要玩家按 F8 交还原角色。F8 保留为手动接管/调试退路。

| 能力 | Bridge 负责 | 第一项验收与后续扩展 |
| --- | --- | --- |
| 背包与装备 | 原生库存、装备槽、装备条件、装备/卸下、实际结果 | 一件护甲换装后原生槽位与效果正确；再扩展武器、盾、护符、负重 |
| 属性叠加 | 发布原生属性与效果，定义其影响 MC 的位置 | 同一件装备不重复减伤；再加入攻击、最大生命、状态与能力修正 |
| 魔法、祷告、战技 | 记忆/选择、施法器与装备条件、请求原生动作、朝向/目标、动作结果 | 一个原地法术正常出手、扣 FP、受打断；再做蓄力、连段和移动战技 |
| 格挡、弹反、处决 | 原生防御动作、时机与命中结果，协调 MC 攻击输入 | 一种盾的弹反与一次处决；不能以“播放动画”代替真实判定 |
| 骑马 | MC 马的召唤、上下马、移动、生命、相机高度，以及隐藏原生角色跟随 | 吹哨召出 MC 马并正常移动/下马；再做跳跃、骑乘施法与受击落马，不要求原生托雷特 |
| 制作与强化 | MC 配方、原生材料/货币消耗、装备发放、结果确认 | 一个明确配方；失败和重启不重复扣料/发装备；强化与战灰另列操作 |
| 场景与遭遇 | 拾取、NPC/赐福交互、生成/激活、死亡与清理事件 | 保留前篇接口，供资源和对局规则使用 |

### R13：当前控制接管会覆盖原生动作位移

**分类：隐藏原生角色施法、战技与弹反上线前必须处理。状态：源码确认的结构缺口，动作策略待验证。工作线 A/Core + B。**

`bridge-base/elden-ring/er-bridge/src/game.cpp::stand_in` 在接管时每轮设置 `NoMove`、关闭原生重力，并把 `hunterPos` 和朝向写回原生物理位置。`service_action` 只处理当前原生交互提示，协议尚未提供完整的装备/施法操作。因此“把按键送给 ER”不足以实现这些能力：动作输入可能被阻止，原生动画自带位移或朝向可能被 MC 同步覆盖。但普通原地法术不一定要把移动权交还 ER，应按动作分别处理。

建议把“哪个系统决定角色位置”显式化，UI 焦点不随内部控制权变化：

- 普通移动：MC 决定移动，Core 对地形与实体接触修正后同步 ER。
- 原生动作：隐藏的原生玩家负责施法与动作结果，MC 按前后摇限制冲突的 Speed、Aura 和输入；普通法术保留 MC 移动，带位移动作单独适配。
- 骑乘：由 MC 马与骑手决定移动，隐藏原生角色跟随，并处理身体/相机/施法点高度，不要求原生骑乘状态。
- 动作结束：核对原生状态、最终姿态和场景身份后恢复普通移动。打断、死亡、读条、断连必须有退出路径，不能只靠固定延时判定完成。

这里描述的是内部动作策略，不要求玩家切窗口或按 F8。首个原地法术通过也不能推定带位移的战技、弹反窗口和骑乘施法全部可用。

### 属性如何叠加

法环库存与装备由法环持有真实状态，MC 物品由 MC 持有。允许双装备，但要为每一类属性指定结算位置：

1. 原生敌人打玩家：当前观察到的原生 HP 损失已经经过法环装备/防御，再进入 MC 伤害处理；不再把同一法环减伤重复乘一次。不同装备组合应测实际差值。
2. MC 普攻打法环敌人：目前 `game.cpp::apply_hit` 根据 MC 伤害换算宿主扣血并施加命中反馈，不等于执行所穿法环武器的一次完整原生攻击。想让 ER 武器影响 MC 普攻，需要单独定义加成/属性转换。
3. 法术、战技等原生攻击：优先由 ER 计算 FP、精力、命中、伤害和异常积累；MC 读取结果。同一动作不能又通过代理攻击重复扣敌人 HP。
4. 制作、兑换、强化：请求带操作 ID、配方/库存修订和结果确认，跨存档扣款/发放要可恢复。结果未知时先核对，不能直接重发。

## 2. 把作弊端能力做成可成长技能

这是正式的玩法目标，放入工作线 C；LB/Meteor 是能力执行后端。Bridge 提供动作与宿主状态，不应把技能经验、解锁条件和等级表写进原生地址适配器。

建议依赖关系：`玩法规则 → 通用能力策略 → LB/Meteor 适配 → 模块执行`。MC 逻辑服务端保存技能点、等级、前置、消耗、冷却与上限；单人用现有集成服务器即可。客户端负责技能图谱、升级预览和输入反馈。

| 技能 | 成长可影响的参数 | 必须统一限制的入口 |
| --- | --- | --- |
| Speed | 解锁、实际水平速度上限、冲刺时长/能量、可用移动模式 | 热键、配置导入、脚本、模式切换，以及原生动作/骑乘期间的互斥 |
| KillAura | 解锁、有效攻击距离、攻击频率、目标数、资源消耗 | 范围设置、穿墙范围、目标选择、实际攻击请求与服务端接受范围 |
| 后续能力 | Fly 时长、视觉感知范围、Velocity 抗击退等 | 每项单独定义效果，避免一个等级默认授权整个客户端 |

等级数值先配置化。例如 Speed I/II/III 可以逐级提高地面速度和持续时间；Aura I/II/III 可以逐级增加攻击距离。数值由单怪与小场遭遇测试确定，本篇不设最终平衡。

对范围可以使用 `有效范围 = min(玩家设置, 技能上限, 当前服务端允许范围)`。Aura 的扫描范围与有效攻击距离分开；等级增加到原版允许距离之外时，必须同时实现合法的服务端交互距离/桥接攻击验证。只提高 LB 的滑杆可能选得到却打不到。Speed 也不能把不同模式里名称相近的 multiplier 当成统一的实际米/秒。

### 是否现在就 fork

核对了固定 LB `e5a0dbf`：`ClientModule.kt` 有模块锁与启用变更入口，`Value.kt` 有设置变更机制，`ModuleKillAura.kt` 有独立 `Range` / `WallRange`，`SpeedGeneric.kt` 包含不同移动模式。因此**两技能原型可先用当前兼容层加最小适配，fork 不是启动条件**；但这些是内部接口，不承诺一个通用脚本覆盖全部行为。

如果目标确定为长期发行的技能客户端，建议在原型验证后维护薄 fork：增加稳定的能力授权/参数约束入口，替换或整合技能 UI，继续追踪上游。技能存档和规则仍留在独立玩法组件，不复制进每个客户端。Meteor 也走同一能力接口；不要同时 fork 两套客户端来实现第一版技能树。

单人限制首先是玩法设计；多人时实际移动、攻击、消耗还需服务端校验。隐藏按钮或限制本地配置不构成可靠的多人权限边界。

## 3. 贴怪穿模与透明

### R12：怪物代理可被攻击，但没有可靠的身体阻挡

**优先级 P1。分类：用户当前报告的游玩缺陷。状态：相关源码缺口已确认，修复与实机复现待做。工作线 A/Core。**

证据在 `bridge-base/elden-ring/mc-bridge/src/main/java/dev/ermc/bridge/entity/ErEntity.java`：构造时 `noPhysics = true`、无重力、`blocksBuilding = false`，`isPushable()` 返回 `false`；位置由宿主更新，代理 tick 不运行普通生物移动/推挤流程。`isPickable()` / `isAttackable()` 处理选取与攻击，不是身体碰撞。`EntityCollisionMixin` / `CollisionGetterMixin` 接入的 `NativeTerrainCollision` 主要提供原生地形接触，未发现完整的怪物身体接触求解。

这支持“MC 玩家可进入原生怪物身体”的定位，但不能据此确认透明来自哪一条渲染路径。相机进入模型后的近裁剪/淡出和合成深度问题都应分别观察，不能先用关闭透明掩盖接触缺口。

建议修复方向：

1. 区分用于选敌/攻击的盒子与用于身体接触的形状。大 Boss 的整体攻击 AABB 不能直接当实心墙，先从普通人形/一个大体型模板的原生身体胶囊或近似形状开始。
2. 玩家移动加入连续接触检测与滑动；怪物主动进入玩家位置时加入有界的重叠分离。Speed 下跨越身体和静止时被怪物挤入都要覆盖。
3. 原生 AI 继续拥有怪物位置，不让 MC 对代理施加普通推力后又被宿主拉回。不能只把 `isPushable()` 改成 `true` 就宣称解决。
4. 区分活体、死亡、消失/卸载和异常快照；按场景/时效清理旧接触，避免留下空气墙。NPC 是否阻挡另配，不由“能否攻击”决定。

验收场景：普通士兵正面/侧面贴靠、怪物走向静止玩家、Speed 冲向怪物、坡道/墙边、一个大体型敌人、死亡移除、切图。记录玩家与宿主坐标、身体形状及相机位置；接触正确后单独检查透明是否仍出现。

## 4. 树、动物、矿物和洞穴的落地方式

当前桥接地形是采样/缓存，不是完整的原版世界生成；`ErBridgeMod` 注册的代理地形不可普通挖掘、无掉落，并禁止以其作为自然生成支持面。仅打开自然刷怪开关不会得到正常的生存世界。

资源分三个阶段，规则都由 MC 服务端执行：

1. **先做真实 MC 资源区。** 在已确认的地表/空腔区域放树、可采矿块、食物与少量动物，使用真实方块、掉落、工具耐久和配方。生成位置核对原生地表、坡度和净空，不覆盖未知区域或原生碰撞代理；地图身份、种子、资源点 ID 与已采状态一起存档，按每局或冷却刷新，避免重载反复刷资源。
2. **再加法环表面采集。** 命中原生表面后按材料映射为石头/泥土/矿物的采集节点；可做右键“转化/标记”再挖的交互。节点提供硬度、工具条件、耗竭状态和掉落，但必须明确这一步不挖掉法环山体。动态可破坏物件沿原生破坏确认单独接入。
3. **独立固定地图补完整地下。** 把确定的地形转换结果保存为持久 MC 世界，再在地图数据明确可用的地下区域生成矿脉/矿洞；MC 单独运行可继续玩这个世界。但 ER 里不会因 MC 生成了洞穴就自动出现相同洞穴，原生怪物也不会自动进入这些新洞。要做共享洞战，先用法环已有洞穴，或单独解决原生几何/碰撞/导航改造。

原版动物/怪物的生成还依赖合适的真实方块、光照、生物群系、难度和数量限制；首版用服务端的区域生成器更容易验证。出生后 MC 生物与 ER 敌人的移动、攻击与死亡交互各自验收，不把“刷出来”当作跨游戏战斗全部支持。

### 右键替换成石头、然后挖掉，可行到哪一步

| 操作 | 可实现的层级 | 限制 |
| --- | --- | --- |
| 法环表面标记为 MC 石头资源，挖后掉石头 | 可优先实现 | 原生表面和碰撞仍在；这是采集，不是挖洞 |
| 用 MC 石头覆盖一个原生物件，再隐藏/禁用该物件 | 可对明确支持的独立物件做原型 | 需要同时处理原生模型、碰撞与生命周期，不能推广到任意山体 |
| 从任意地面/墙里挖出一个立方体空洞 | 高成本研究项 | 需要修改/替换原生网格及碰撞、更新采样缓存与存档；很多地形是大块三角网格，无法按 MC 单格直接删除 |
| 增加 MC 方块，令它成为 ER 物理障碍 | 已找到可参考的开源实现 | 要做版本适配、游戏线程调度、碰撞过滤、增删/切图清理与实机测试 |

当前仓库仍没有 MC 方块反向注册 ER 物理刚体/导航的完整路径，所以“MC 玩家能站在墙上”不代表“法环怪物会被墙挡住”。地形同步还应避免 ER 射线采到我们新增的方块后又把它写成不可挖的原生代理，形成自反馈。

即时**新增/移除我们自己创建的碰撞体**和即时**从原有复杂地形挖掉局部几何**是两个难度不同的功能。挡住怪物、挡箭/法术、挡近战、AI 绕路也分别验收；Havok 物理体不会自动修改法环导航网格。

## 6. Debug 工具选择与指定怪物测试

优先组合是 **Hexinton 指定怪物生成 + TarnishedTool 观察/复现**，先分开启用和验证，各自只开当前需要的功能，避免两个工具与 Core 同时写相机、HP 或速度导致结果不可解释。

### R03 的新增触发条件：外部刷怪工具共用 debug set

原 R03 仍未解决。`game.cpp::remove_test_enemy` 会遍历整个 debug set 并 `ForceDeath`，接管结束也可能触发该清理。准备使用外部刷怪器后，这不再只是未来玩法问题：**外部生成的测试怪物可能被一并删除。**

在把外部刷怪与接管切换纳入重复测试前，先修为只清理本组件确实创建的实例：记录会话/场景/生成身份，原生对象失效时放弃操作，不能跨切图保留裸指针，也不能单凭“在 debug set 中”认领对象。生成确认还应防止外部工具请求被误认为自身请求结果。

建议实机顺序：

1. 确认标题版本与 EXE 产品版本，再选对应工具；继续使用现有已验证的离线 Bridge 启动方式。工具解压到独立目录，不改写当前加载 DLL；本轮尚未执行安装。
2. 固定一份测试存档与地点，先用现有士兵和普通场景敌人记录原始接触问题。观察工具先只开目标状态/盒子显示，保持伤害、速度、相机修改关闭。
3. 修复自身生成实例的确认/清理归属，再用 Hexinton 单独生成一个指定普通敌人，确认 F8/清理不会误删外部实例。
4. 执行 R12 的接触与透明验收；随后一个大体型敌人复测。最后用一堵墙分开测玩家、ER 怪物、箭/法术与近战。

## 7. 下一轮可执行顺序与仓库决定

1. **Core 修复包：R12 身体接触 + R03 刷怪归属。** 保留现有受击与 LB 验证记录；补必要的接触/清理诊断，在 Windows 上取得同场景前后证据。
2. **Bridge 首个完整切片：背包 → 一件护甲装备/卸下 → 一种原地法术。** UI 全程留在 MC，验证原生状态、单次扣款/伤害与动作打断；这里开始建立内部动作控制权协议。
3. **玩法切片：两种资源 + Speed / Aura 两技能图谱。** 一段获取材料/经验、解锁能力、击败敌人的流程，数据驱动等级与代价，测参数越界和配置切换。
4. **物理实验：一堵 MC 墙注册为 ER 静态碰撞。** 参考 EldenCraft 的对象生命周期，单独评估普通敌人和投射物；这项不等待完整技能树，也不以“AI 暂不会绕路”否定碰撞价值。

Bridge 先在当前仓库划分独立组件/API，完整操作范围现在就写清楚。等最小动作协议、实际依赖和配套发布方式稳定后再决定独立仓库；新仓不会自动解除对 Core DLL/协议的依赖。能力客户端需要 fork 时另建薄 fork，与 Bridge 内容组件的拆仓是两个决定。当前没有创建新仓库、fork、修改两份 LB 计划或改写实机通过状态。
