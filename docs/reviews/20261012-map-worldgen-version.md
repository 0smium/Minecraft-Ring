# 固定地图、MC 地下世界与版本选择 review

2026-10-12 · 研究与架构建议，未实现、未做新增实机验证

代码基线：`dev/lb-poc` / `3e66a0b2780b72b60eeb0197bbc01c28db47be0b`

关联：[玩法路线](../gameplay-roadmap.md) · [玩法准备度 review](20261012-gameplay-readiness.md)

## 1. 本轮结论与范围

建议继续使用 Minecraft 1.21.1 + Fabric + LiquidBounce v0.22.0 / Build #3530 完成当前 A 工作线。原 LB 开发方案和实验计划不变，不在本次研究中升级或降级制品。

后续地图目标可以是：同一份服务端权威地图，支持不启动法环的 MC 探索/玩法开发，也支持开启法环后的原生画面与遭遇。地下资源、挖矿、建造、MC 生物和对局规则交给 MC；原生法环敌人的 AI、动作与存活状态仍由法环负责。这需要新增地图和模式能力，当前保存的碰撞不等于已完成地图移植。

UHC 需要的是每局共同、可复现的初始世界和统一判定，并非必须预生成全图，也不是地图永久不可修改。预生成选定赛区适合本项目；挖矿、放置、开门、容器和遭遇进度属于本局变化，新一局从模板重置。探索后才生成的区块也必须由服务端按同一版本、配置和种子生成，不能由每位玩家各自采样出不同世界。

## 2. 已确认的底座事实

以下是源码/已有记录确认；影响与处理方案是本轮推导。

| 事实与代码位置 | 对需求的影响 |
| --- | --- |
| `WorldBootstrap.create()` 创建只有一层 AIR、无结构的 `FlatLevelSource`，关闭自然生物生成 | 当前不是原版生存地形，没有等待开启的地下矿洞/矿石；需要新的生成流程或导入世界 |
| `TerrainBlock` 使用空模型；`TerrainShapeBlock` 继承这一渲染行为 | 保存的碰撞本身不可见，不启动 ER 不会自动看到完整交界地 |
| `TerrainShapeBlockEntity` 保存形状，`TerrainRegeneration` 保留已存碰撞 | 可作为静态地图数据的一部分，但覆盖范围、已测空气、材料和生成完成状态仍需补齐 |
| `TerrainManager` 的粗地形 `THICKNESS = 2`，细采样围绕玩家 | 它不是完整实心地质模型；不能在两层碰撞下直接期待原版矿物与洞穴 |
| `TerrainManager.onServerTick()` 在宿主不在线/映射不可用时调用 `floorAround()`；启动会请求回到宿主位置 | 单独运行 MC 需要明确模式，不能把掉线回退当作独立地图模式 |
| `CoordMap` 按区域保存锚点，反转 Z；不同区域间隔 32768，参考高度 MC_Y=100 | 地图包必须固定区域/坐标映射，评估完整地形的垂直范围；不同玩家不能各自以出生位置重新锚定 |
| `compositor.cpp` 将 MC 颜色/深度、手部和 HUD 合成进 ER；被 ER 深度遮挡的 MC 世界像素会被丢弃 | MC 效果有现成合成通路，但原生地表仍可能挡住新洞口和地下内容 |
| `ErEntityRenderer` 不绘制原生怪物模型；`LifeBridge` 同步宿主死亡与回归 | 离线地图不会自动获得 ER 敌人；地下移动不能继续无条件拖着宿主角色钻进原生地图下方 |

源码入口均在 `bridge-base/elden-ring/`：Java 文件位于 `mc-bridge/src/main/java/dev/ermc/bridge/`，`WorldBootstrap`、`ErEntityRenderer` 位于 `mc-bridge/src/client/java/dev/ermc/bridge/client/`，合成器位于 `er-bridge/src/compositor.cpp`。已有 LB GUI/合成成果和未验证项仍以 [检查点](../experiments/20261012-checkpoint.md)为准。

## 3. 区分三个地图能力

| 能力 | 不启动 ER 时的结果 | 还缺什么 |
| --- | --- | --- |
| 静态碰撞持久缓存 | 有部分碰撞数据，当前没有完整可见场景 | 完整覆盖与有效性、显式离线行为、可见表示 |
| 可独立打开的 MC 地图 | 目标是看得到、走得动、能采集建造的交界地方块版或近似版 | 几何转换、方块/材质映射、地下填充、资源生成、独立运行模式 |
| 保持 ER 原画质与原生遭遇的联动地图 | 仍需运行 ER 提供画面、AI、原生装备等 | 在前两项之上协调宿主与 MC；缓存不替代宿主进程 |

碰撞数据主要说明哪里有表面/实体，不自动告诉生成器哪里该放橡木、草方块、铁矿或宝箱。即使能读取原生材料标签，也要建立分类到 MC 方块/资源的映射。当前射线结果更不能还原贴图、植被和建筑细节。首先可以按区域配置方块调色板和资源规则，再研究更丰富的场景信息。

“单开 MC”可以指装有本项目地图模组的 Fabric MC，不必要求纯原版。若要无模组 vanilla 客户端也能打开，必须另做原版方块导出，替换 `erbridge:*` 自定义方块/实体，并接受形状精度损失。不能直接删除模组后把同一份自定义存档当作可移植交付物。

建议地图包表达稳定的区域、变换、地图/资源版本、生成器版本、种子和配置、已生成三维范围、已知实心/空气/未知、静态地形、动态对象及可挖掘范围。首版用现有 MC 存档加少量元数据即可，不要求先设计通用引擎格式。

匹配开始时固定地图模板和配置；每局使用独立副本或可验证的重置记录。矿石一旦被挖掉、木材被采集或玩家挖出通道，重连和重采样不能把它们恢复。静态生成、MC 可变区域与原生动态对象要有明确归属，不能让多个生成器同时拥有同一块空间。

复制 MC 地图模板不会复位 ER 的剧情、Boss 死亡标志或原生库存。每局原生遭遇需要可重置的模板/激活方式和结果确认，不能把“MC 地图已重置”当作两款游戏都已恢复初始状态。

## 4. 地表保留法环，地下使用 MC

### 可行的目标

按法环区域几何确定地表和必须保留的原生空间，在分配给 MC 的地下体积里生成石头/深板岩、矿物、洞穴、含水层及配置的结构；在允许的表面补充可采集的树木、食物和其他原版资源。挖矿、熔炼、制作、附魔、建筑和 MC 战斗随后可以复用正常 MC 系统。

实现方式可以是自定义生成器，也可以先离线生成地下区块再拼接并保存。原版的矿石/结构放置规则可供复用，但需要正确的石材标签、生物群系、生成阶段、邻区块状态和高度范围；不能只把生成器名称改成原版，或安装世界生成模组，就假定它会在现有虚空世界下面补齐矿洞。已生成区块也不会因此自动重新执行所有生成阶段。

第一版先用原版内容验证完整发育。补给覆盖木材、食物、石料、煤铁，以及玩法实际需要的金、钻石、皮革/纸等，避免“有矿洞但配方缺关键材料”。要恢复适当的光照、方块更新、自然生物与掉落规则；当前桥接的环境/生死设置需要按模式协调。

### 同坐标无缝衔接的实际障碍

1. **地表仍在。** 挖掉 MC 方块不会在 ER 山体上开洞。需要选择原有洞口，或实现受控区域的原生表面隐藏/裁切，并补齐洞口内壁；普通深度合成只会叠加 MC 像素，不会自动做几何减法。
2. **原生地下空间不能被填埋。** 桥下、洞窟、地下城和多层建筑都需要保留三维空腔，不能只拿 X/Z 最高地表向下灌满石头。原生剧情切图/独立区域也不一定是同一连续坐标空间。
3. **宿主角色不能无条件跟随。** Steve 进入 MC 新洞穴时，ER 对应位置可能是实心、未加载区域或死亡区。需要暂停该玩家的宿主位置/碰撞/死亡与回归耦合，将宿主保持在已验证安全状态；离开时先确认宿主区域就绪再恢复。不能只全局禁用死亡逻辑。
4. **画面需要切换。** 地下由 MC 提供完整不透明场景、光照和声音，不能继续完全依赖 ER 背景与重打光；入口附近需要明确遮挡与过渡规则。现有 F8 是把控制交回 ER，并不是这个地下模式。
5. **敌人活动范围。** MC 生物与后续 MC 玩家可以在 MC 洞穴活动；原生 Boss 不会自然获得新洞穴的碰撞、寻路或加载支持。让 ER 敌人追入新洞穴属于另一项原生能力，不能用地图已生成来宣称已实现。

建议先通过一个明确入口连接到 MC 地下区域或独立维度，验证采集—制作—战斗—返回。随后用同一资源区验证同坐标出入和视觉过渡；“真正无缝”保留为目标，不能把传送版写成已经实现无缝。独立维度版的缩圈也必须使用同一对局时钟和明确的坐标/边界规则，避免地下成为永远安全区。

离线地图用于开发地图、资源和 MC 规则很有价值。离线测试可使用明确标注的 MC 敌人/测试遭遇；不代表 ER Boss 的生成、动作或死亡桥接通过。

## 5. 缩圈与边界

建议由 MC 服务端决定边界、时钟和圈外效果，客户端绘制边界墙、粒子、地图标识与倒计时，并进入现有合成通路。原版 WorldBorder 是方形候选；圆圈或感染区使用自定义区域判定与可视化。

这意味着玩家在 ER 合成画面里看到 MC 边界，不代表原生法环突然新增一道有碰撞的墙。ER 敌人不会自动被 WorldBorder 阻拦，也不会自动受到圈外伤害；如模式需要，应通过内容桥接单独执行和确认。玩家伤害只由明确的一条规则路径结算，避免 MC 和 ER 各扣一次。

当前没有边界专项验收。需要检查透明边界是否被捕获、深度遮挡是否正确、地下是否可见/生效、LB 移动/传送越界、F8/读条/断连和退出模式后的规则恢复。单人集成服务器可先验证；多人共用地图仍需此前 review 中的玩家—宿主对应与共享敌人同步改造。

## 6. Minecraft 与 LiquidBounce 版本选择

2026-10-12 查询官方发布页：1.21.1 的公开稳定版为 [LB v0.22.0 / #3530](https://liquidbounce.net/download/3530)，官网将该 MC 分支标为 discontinued；最新稳定发布是 [LB v0.41.0 / #18191，MC 26.3](https://liquidbounce.net/download/18191)，发布日期 2026-10-06。不是对未来发布的承诺，也不把稳定发布与 nightly 混为一谈。

| 方案 | 项目收益 | 成本与判断 |
| --- | --- | --- |
| 保留 Fabric 1.21.1 + LB 0.22.0 | 复用现有 Bridge 与已记录共载成果；有足够的地图/资源/工具模组候选 | 旧 LB 分支不再跟随新功能；当前继续使用并固定制品 |
| 迁移到 MC 26.3 + LB 0.41.0 | 新 LB 有 add-ons、扩展 HUD/菜单能力和多项修复 | MC API、Mixin、渲染抓取、实体/存档及依赖需移植和回归；不是换一个 LB JAR。待明确需要新能力时独立试验 |
| 降到 MC 1.8.x / 1.8.9 | 可研究旧小游戏实现和旧 PvP 行为 | 当前 Fabric API、注册/实体/方块、数据与渲染路径需大量回移；现有世界/内容无法默认兼容。不建议为了旧插件数量整体降级 |

新版 add-ons 是实际可能有价值的收益，不能只用“版本新没意义”排除。其 Script API 已改为 add-on，接口和兼容性需重新核对；也不能假定新扩展接口已经稳定或桥接可直接接入。升级前先列出旧版满足不了的必需功能，再用独立分支验证启动、颜色/深度/手部/HUD、一次地形行走、实体战斗及需要的 LB 模块，验证后决定是否迁移主线。

作者选版原因：本 Fork 的初始 Windows 引入提交 `003eac9` 已是 1.21.1；[原始 upstream](https://github.com/justbustin/minecraft-crossover-bridge) 的 README 和已检查源码也使用 1.21.1。能确认技术谱系继承，未在已读 README/历史中找到作者解释最终选版动机；“可能为了稳定/生态”只能作为推测，不能当作作者结论。当前项目选择 LB 0.22.0 的明确原因则是与已有 1.21.1 底座匹配。

[ViaFabricPlus](https://github.com/ViaVersion/ViaFabricPlus) 和 [LB 下载页](https://liquidbounce.net/download)提供不同服务器协议的连接能力。这不让 MC 26.3 进程加载 1.21.1 的 Bridge JAR，也不把旧 Bukkit 插件变成 Fabric 模组。现代客户端连接旧服务器仍不能让旧服务端天然理解当前自定义碰撞、实体和资源。不要把协议互通当成引擎/模组二进制互通。

## 8. Hypixel 规则与之前项目的复用

用户提到以前移植过 Hypixel 逻辑，本轮没有拿到该旧仓库源码，不能报告具体代码复用比例或移植工期。下一轮只需检查旧项目的构建文件、插件入口、API/NMS 依赖和一条完整规则路径。

| 旧内容形式 | 迁移到当前 Fabric 的方式 |
| --- | --- |
| 比赛阶段、计时、队伍、配方/掉落设计、胜负规则等独立逻辑 | 保留规则与数据，给服务端事件/世界读写接新适配器 |
| Bukkit/Spigot/Paper 事件、调度器、背包 GUI、计分板、世界操作 | 重写平台接入部分；不能直接把插件 JAR 放进 Fabric mods |
| 1.8 NMS、数据包、反射、实体实现、旧物品元数据/战斗时序 | 逐项重新实现或替代，通常是迁移风险最高的部分 |

[Paper 官方说明](https://docs.papermc.io/paper/adding-plugins/)明确区分 Paper 插件与 Fabric/Forge 模组。规则设计的复用、代码复用和现成 JAR 复用是三个层次。若将来旧插件非常关键，可另评估现代 Paper 侧的玩法服务和新的网络适配；当前 Bridge 的自定义碰撞/代理实体已经在 MC 逻辑服务端工作，换 Paper 并非零成本。首版继续 Fabric 服务端，不预设混合服兼容层可用。

若需要接近 1.8 的 UHC 战斗，应在选定现代版本上明确攻击节奏、格挡、击退、治疗和装备数值，再实测；单纯去掉攻击冷却不能叫完整 1.8 PvP。地形与资源是否有趣、旧规则的还原程度和 MC 引擎版本应分别评估。

此前空洞骑士《疫潮》、黑夜君临式远征等项目可以复用阶段、遭遇、缩圈、奖励与结算的设计；具体运行桥接仍各自适配。已有原生联机/玩法底座也应计入选择。2D 空洞骑士不必为了规则复用强行套入 3D MC 世界；先复用数据和规则边界，不先建设跨游戏通用框架。

## 10. 下一项可评审实验

继续三个工作线，不增加“必须立刻完成全图转换”的新门槛。A 先完成既定 LB 单项成果；地图工作由 A/C 共同约定，涉及宿主暂停/恢复与敌人活动范围时由 B 接入。

选一块候选小区域，例如 128×128 或 256×256 方块作为地图实验尺度，包含平地、坡面、桥下/门洞和一个入口。数值可按实机调整，不作为承诺的地图上限。

1. **独立地图。** 导出可见且有碰撞的静态样本及固定坐标。关闭 ER，仅运行装有必要模组的 MC，能探索；重启后几何/坐标不漂移，未知区不被当成已完成。
2. **真实发育。** 生成有限地下和地表资源，玩家不靠临时命令能从木材到铁制工具，挖出的通道与采集结果重启后保持；生成不可填埋受保护原生空间。
3. **联动进出。** 回到同一 ER 区域，两端坐标吻合；从入口进入 MC 地下再返回，画面、光照、生命、相机和控制权正确，没有原生死亡/回归打断。传送版与同坐标版分别记录。
4. **边界。** 从服务端改变圈大小，在最终 ER 合成画面中录屏确认；地上/地下都按同一时钟生效，切模式后恢复。边界对原生敌人的作用按已实现能力单独报告。
5. **规则移植。** 读取用户旧 Hypixel 项目，只选一条“阶段切换或击杀奖励”完整路径，判断哪些代码可抽出，哪些平台调用要重写。

完成这些后再决定是否扩大地图、增加世界生成模组或启动版本迁移。独立 MC 模式和测试后端结果必须与 ER 实机结果分开记录；本文件只记录研究，不将上述验收标记为通过。
